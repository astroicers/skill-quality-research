# 讓 LLM 當評審時,你的量測會從哪裡漏

> 這份文件不依賴本專案的研究結論。你不必同意「星數關聯打包面不是工藝」,
> 底下每一條仍然適用於**任何「用 LLM 評判產出品質」的系統**。
>
> 來源:2026-08-17/18 兩輪 craft 判定一致性量測(3 位審查者 × 15 個 repo × 4 維度 × 2 輪
> = 360 個標記)。**下列五類污染源,四類是審查者自己揭露的,不在我原本的隔離清單裡;
> 其中三類是我在「修正上一輪缺陷」時親手製造的。**

---

## 0. 為什麼「隔離清單」這種做法會失效

直覺做法是列一份「審查者不准讀的檔案」。兩輪下來這份清單**每一輪都被繞過**,
而且不是被違反 —— 三位審查者都遵守了清單,污染從清單**沒想到的地方**進來。

原因是:污染的載體不是「檔案」,是**資訊路徑**。而資訊路徑至少有五條,
其中兩條你不控制。

---

## 1. 判準文件自我定錨(rubric self-anchoring)

**現象**:判準檔裡的「證據引用」欄位具名了受評對象,而且帶著結論。

本案的 `rubric-manual-dimensions.yaml` 有 `evidence_refs` 欄位,寫著像
`browser-act(20+ 變體轟炸=反例)`、`blader/humanizer(33 pattern 皆附 why)` 這樣的條目
—— 那是 rubric 的正當設計(讓判準有具體錨點),但當受評樣本與那些引用重疊時就是災難。

**量化證據**(這是本文最硬的一條):

| 分組 | n | 成對一致率 | Fleiss κ | 分歧數 |
|---|---|---|---|---|
| **被 rubric 具名的格** | 5 | **1.000** | **1.000** | **0** |
| 其餘 | 55 | 0.824 | 0.628 | 14 |

**被具名的 5 格全數一致、零分歧。** 這不是巧合,是定錨。

**緩解**:發給審查者的判準用**程式產生的遮蔽版**,不要手工改副本
(手工副本會與正本漂移)。遮蔽後**逐行比對**確認只有預期的行被改、行數不變。

---

## 2. 去識別化失敗:描述本身可以唯一回推

**現象**:你把 repo 名遮掉了,但敘述唯一指向它。

本案 L-004 的例外條款我寫了兩個「匿名」舉例:

| 條文裡的文字 | 唯一指向 | 驗證 |
|---|---|---|
| 「某 skill 直述五條 ADHD 神經科學事實」 | 樣本中唯一的 ADHD skill | 其正文即 `Five facts drive every rule below` |
| 「記錄自家 index.html 的 CSS class」 | 樣本中唯一的簡報樣式 skill | 其正文即 `CSS classes and HTML patterns used in presentation/index.html` |

兩處都不透露分數,但**都直接排除了該格的 `n/a`** —— 等於替審查者做掉了判定流程的第二步。
一位審查者明說:

> 沒有那一行,我很可能會判 n/a。我這一格應視為被定錨,不是獨立判定。

**緩解**:遮蔽器要處理的不只是名字。舉例要麼抽象到不可回推,要麼整段從審查者版移除。
**寫條文時就要意識到:唯一可識別的實例 = 定錨源。**

## 3. 文件化修正的動作,污染了驗證該修正的測試

**這是最反直覺的一條,也是我認為最普遍會被踩到的。**

第一輪發現某判準有邏輯矛盾 → 我改寫它,並依良好實踐寫了「**為什麼要明訂**」理由段
(好文件本來就該解釋 why)。第二輪的遮蔽版原封留著:

```
一致性量測顯示 L-002 κ=0.597,是四維中第二弱。
...(Fleiss κ=0.400,14 個分歧佔 8 個)...
分歧格 〔已遮蔽〕(R1=mixed、R2/R3=good)
```

名字遮了,**修正的方向沒遮**。一位審查者指出具體效果:

> 讀那個 repo 之前,我已經被告知舊措辭讓這類 skill 拿不到 good、而這是個已修的缺陷
> —— 那把我推向 good。我仍然讀了原文才判,但那個 prime 在。

**結構性衝突**:好的判準文件必須解釋「為什麼這條規則長這樣」,而「為什麼」
必然包含**前一次觀察的結果**。所以判準檔天生會累積上一輪的答案。

**緩解**:理由段與判準本體分離 —— 判準檔只放規則,理由放在不發給審查者的決策紀錄裡;
或遮蔽器連理由段一起剝。**別指望靠自律,寫的時候不會意識到。**

**推論**:這也意味著「量測 → 修 → 再量測」這個迴圈,**每跑一輪就污染下一輪**。
除非你在每輪之間都做這個切割。

## 4. 確定性層的預判洩漏給質化層

**現象**:你先跑一個 deterministic 檢查,把結果交給 LLM 當輸入 —— 但那份輸出裡
夾帶了**對 LLM 要判的事情的預判**。

本案的 lint 輸出有個 `craft_llm_todo` 清單,每筆帶 `desc_has_trigger: true|false`。
那正是四個 craft 維度中第一個維度要判的事。審查者在建立閱讀清單時就看到了那些布林值。

值得注意的是:審查者**有幾次不同意那個 flag**(regex 讀不出中文的「當…時使用」句式、
看不見某 skill 顯式的呼叫/終止契約)。**所以那個預判不只是定錨,還是個會錯的定錨。**

**緩解**:給審查者的副本剝掉任何對其判定範圍的預先結論。保留路徑清單即可。

## 5. Harness 自動注入受評對象的指令檔 ⚠️ 這條是安全問題

**現象**:讀取受評 repo 底下的檔案時,agent harness 會把**該 repo 自己的
`CLAUDE.md` / `AGENTS.md` / `.claude/rules/*.md` 當作「專案指令」注入審查者的 context**,
未經請求。

三位審查者**各自獨立**踩到並揭露。其中一位把它排在第一位:

> (a) 這是協定內部的一個活的 prompt-injection 面 —— **一個惡意 repo 可以放一份
> `CLAUDE.md` 直接指示審查者如何評分**。
> (b) 它給了我 repo 級的上下文,而讀取順序不同的審查者不會拿到 ——
> 這是不受控的審查者間變異,且它**實質影響了我對某兩個 repo 的判讀**。

實際注入內容包括強烈的自我宣傳(`94% PR rejection rate`、`extensively tested and tuned`)
與一段對閱讀中 agent 說話的 `Prompt Defense Baseline`。三位都把它當資料、都沒有遵循
(符合供應鏈警覺原則),**但那條路徑存在,而且是評審協定自己走進去的**。

### 這條對誰重要

**任何在 agent harness 裡建自動化 repo 審查 / code review / 品質評分系統的人。**
你的評審讀取目標 repo 這個動作本身,就讓目標 repo 有機會對評審說話。

### 緩解

把要評的檔案**複製到一個中性目錄**再交給評審,只帶必要檔案,
不帶 `CLAUDE.md` / `AGENTS.md` / `.claude/rules/` / hooks / scripts。

本專案的實作:[`scripts/extract_rater_corpus.py`](../scripts/extract_rater_corpus.py)
—— 383 MB 的完整 clone 縮成 939 KB 的純 SKILL.md 語料,實測注入面 0 命中。

## 6. 附帶結論:κ 在小樣本上解析不了判準修訂

這不是污染,但它決定了上面五條「該修到多精細」。

第二輪同基準比對(兩輪都排除定錨格,n 完全相同):

| 維度 | 判準有改? | Δκ |
|---|---|---|
| 維度 A | ❌ **沒改** | **−0.213** |
| 維度 C | ❌ **沒改** | **−0.319** |
| 維度 B | ✅ 改了 | −0.068 |
| 維度 D | ✅ 改了 | +0.091 |

**兩個判準完全沒動的維度,變動幅度比改過的還大。** 用未改動維度的實測 Δ 反推:

```
|Δκ| 平均 0.266  →  SD(κ) ≈ 0.188  (n=14)
要解析 0.1 級效果  →  每維度需 n ≈ 404
```

本研究母體 97 個 repo、可用樣本 54 —— **用光母體還差 7.6 倍**。
(粗估自兩個觀測值,不是 power calculation;但量級結論不受影響。)

**兩件可帶走的事**:

1. **成對一致率比 κ 穩定得多。** 兩輪整體 PA 只差 1.8pp(0.824 → 0.806),
   而分維度 κ 排序完全洗牌。κ 對邊際分布敏感,小樣本下極不穩 —— **兩個數字必須併看**。
2. **真正有產出的不是 κ,是審查者的分歧筆記。** 三位獨立讀出同一個邏輯矛盾、
   兩位獨立發明了完全相同的裁決規則、四類污染源全靠他們揭露 ——
   **那些發現完全不需要 kappa**。

所以本專案的裁定是:**保留機制,丟掉統計量。** 派 2–3 位審查者只收分歧與卡點筆記,
不算 kappa。不需要靠樣本量撐統計效力,成本降一個量級,而且那是唯一被證明有效的部分。

## 檢查清單

建 LLM-as-judge 系統時,逐條問:

- [ ] 判準檔裡有沒有具名受評對象?與本次樣本重疊嗎?
- [ ] 「匿名化」的舉例能不能被唯一回推?
- [ ] 判準的**理由段**有沒有洩漏上一輪的結果或修正方向?
- [ ] 交給 LLM 的 deterministic 輸出,有沒有夾帶它要判的事的預判?
- [ ] 讀取受評對象時,harness 會不會把對方的指令檔注入評審 context?
- [ ] 你的樣本量能解析你想偵測的效果嗎?(不能的話,收筆記別收數字)
- [ ] 有沒有一個欄位讓評審**主動揭露**你沒想到的污染源?

**最後一項是回報率最高的。** 本文五類污染有四類是這樣被發現的 ——
只因為 brief 裡有一句「若你發現任何我沒列進禁讀清單、但會定錨你的東西,請寫進
`contamination`;誠實記錄不會被懲罰,隱瞞會讓整批資料作廢」。
